# План рефакторинга проекта

## 1. Проект
Проект Лабораторной работы №2 в рамках дисциплины "Высокоуровневые методы информатики и программирования" реализует консольную систему контроля доступа к иерархическим ресурсам на языке Kotlin.  
Ключевые компоненты:

- `ResourceNode` — модель ресурса древовидной структуры.
- `AccessControlService` — управление правами доступа к ресурсам.
- `authenticate()` и `computeHash()` — функции аутентификации и хеширования.
- `main()` — обработка аргументов CLI, запуск логики, управление процессом.

## 2. Анализ нарушений SOLID

**Single Responsibility Principle**  
Место: `App.kt`, функция `main()`  
Нарушение: функция выполняет сразу несколько задач — парсинг аргументов, валидацию входных данных, аутентификацию, авторизацию, проверку объёма ресурса и завершение процесса.  
Исправление: разделить обязанности. Вынести логику в отдельные модули: парсер аргументов, сервис аутентификации, сервис авторизации, оркестратор приложения.

**Open/Closed Principle**  
Место: `AccessControlLogic.kt`, функция `parseOperation()`  
Нарушение: при добавлении новой операции (например, "delete") требуется изменять тело функции `parseOperation()` через расширение `when`.  
Исправление: заменить жёстко закодированный `when` на конфигурируемый маппинг (например, `Map<String, Operation>`) или стратегию парсинга, чтобы поддерживать расширение без модификации.

**Liskov Substitution Principle**  
Место: в программе нет наследования между пользовательскими классами (используется только `enum class Operation`).  
Нарушение: отсутствует. Принцип не применим.

**Interface Segregation Principle**  
Место: отсутствуют интерфейсы.  
Нарушение: компоненты зависят от конкретных классов (`AccessControlService`, `PathResolver`), что нарушает гибкость.  
Исправление: добавить интерфейсы для слоёв приложения — можно ввести их ради формирования луковичной архитектуры (см. следующее задание). Предлагается:
- `IAuthService` — для аутентификации,
- `IAuthorizationService` — для проверки прав,
- `IResourceRepository` — для работы с ресурсами.

**Dependency Inversion Principle**  
Место: `App.kt`, функция `main()` напрямую создаёт `AccessControlService`; `checkAccess()` принимает конкретный тип `AccessControlService`.  
Нарушение: высокоуровневые модули зависят от низкоуровневых деталей, а не от абстракций.  
Исправление: работать через интерфейсы. Все модули должны зависеть от абстракций (`IAuthorizationService`), а не от конкретных реализаций.

## 3. План

| Этап | Изменение | Цель |
|------|----------|------|
| 1 | Вынести логику аутентификации в класс `AuthService`, реализующий интерфейс `IAuthService` | Соблюдение SRP |
| 2 | Создать `CliArgumentParser` для обработки аргументов командной строки | Разделение обязанностей |
| 3 | Ввести интерфейсы `IAuthService`, `IAuthorizationService`, `IResourceRepository` | Поддержка DIP и ISP |
| 4 | Заменить `parseOperation()` на расширяемый маппинг операций | Следование OCP |
