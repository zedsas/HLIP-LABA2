# План внедрения чистой архитектуры

1. **Цель** — разделить проект на слои с чёткими зонами ответственности, чтобы изменения в одном слое (например, смена CLI на REST API) не требовали переделки бизнес-логики.

2. **Предлагается выделить следующие слои**:

| Слой | Описание | Классы / Компоненты (из текущего проекта) |
|------|--------|------------------------------------------|
| **1. Core (Entities)** | Содержит бизнес-сущности и доменные правила | `ResourceNode`, `Account`, `Operation`, `ExitCodes` |
| **2. Application (Use Cases)** | Логика приложения: аутентификация, проверка доступа, валидация объёма | `checkAccess()`, `authenticate()`, `parseOperation()` |
| **3. Interface Adapters** | Адаптеры, преобразующие данные между внешним миром и ядром | `PathResolver`, `AccessControlService`, `CliArgumentParser` (будущий), интерфейсы `IAuthService`, `IAuthorizationService` |
| **4. Infrastructure (Frameworks & Drivers)** | Работа с CLI, сторонними библиотеками, запуск приложения | `main()` в `App.kt`, `kotlinx.cli`, `.sh`-скрипты (`build.sh`, `run.sh`) |

3. **Пояснение**:
- Сейчас все компоненты находятся в одном слое (в основном в `App.kt` и вспомогательных файлах).
- После реструктуризации зависимости будут направлены **внутрь**: Infrastructure → Adapters → Use Cases → Entities.
- Бизнес-логика (`checkAccess`, `authenticate`) не будет знать о существовании CLI или `kotlinx.cli`.
